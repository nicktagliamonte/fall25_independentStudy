================================================================================
VN-IPFS DHT INTEGRATION PLAN
================================================================================
Problem Statement: Current read operations exhibit O(N) worst-case complexity
(broadcast storm) because content routing requires explicit provider hints.
The system lacks distributed lookup capability.

Solution: Integrate Kademlia DHT for O(log N) content routing with Prefix Hash
Tree (PHT) overlay for regex/wildcard query support per the new document.
DHT + PHT together form the core routing stack.

Reference Documents:
- p2pTSforIPFS4.txt (vn-IPFS Architecture v1.4)
- info.txt (DHT/Kademlia/PHT/IBLT research notes)
- https://github.com/libp2p/go-libp2p-kad-dht (chosen DHT library)

PHASE 3: PREFIX HASH TREE OVERLAY (Required Component)
================================================================================
Goal: Enable pattern matching queries (e.g., "image_*") without O(N) broadcast.
PHT sits atop the Kademlia DHT as a required layer in the routing stack.

From info.txt research:
- Standard DHT: O(N) for wildcards (must flood)
- PHT with Bloom filters: O(log N + f*N) where f = false positive rate
- For 10,000 nodes: ~20 messages vs. 10,000 messages

3.1 Prefix Hash Tree Implementation
    --------------------------------
    File: internal/pht/tree.go (new)
    
    Concept: Instead of hashing whole filename, hash prefixes to create
    navigable tree structure over DHT.

    [x] Implement tree navigation for prefix queries
    [x] Handle node splitting when bucket exceeds MAX_BUCKET_SIZE
    [x] Integrate with Kademlia DHT as underlying storage

3.2 N-Gram Bloom Filter Layer
    --------------------------

    Purpose: Enable "middle-of-string" wildcards (e.g., "*forest*") by
    indexing n-grams in Bloom filters.

THEORETICAL DEFENSIBILITY NOTES
================================================================================

1. Why Kademlia?
   - O(log N) lookup is mathematically proven (see original Kademlia paper)
   - XOR distance metric provides symmetric, unambiguous routing
   - Self-organizing: no central coordination required
   - Well-studied failure modes and mitigations

2. Why PHT for Regex?
   - Standard DHTs require exact key match (hash collision)
   - PHT provides logical structure over flat hash space
   - Bloom filters add probabilistic pruning: O(log N + f*N) << O(N)
   - From info.txt: 10,000 nodes â†’ ~20 messages vs. 10,000 messages

3. Why IBLT for Sync?
   - Standard set exchange: O(|set|) bandwidth
   - IBLT difference: O(|difference|) bandwidth
   - Critical for high-churn networks where full sync is prohibitive
   - XOR-based operations align with Kademlia's XOR distance

4. Trade-offs Acknowledged:
   - DHT maintenance overhead (k-bucket refresh, routing table updates)
   - PHT storage overhead (multiple prefix entries per file)
   - Bloom filter false positives (tunable, ~1% typical)
   - IBLT may fail to peel if undersized (recoverable by resizing)

5. Alignment with vn-IPFS Spec:
   - DHT for O(log N) exact-match metadata queries 
   - PHT overlay for prefix/substring queries (required component) 
   - P2P Tuple Space for admin tasks (accepts O(N) messaging) 
   - Replication vectors (Near/Mid/Far) 
   - Automatic partition handling and repair
