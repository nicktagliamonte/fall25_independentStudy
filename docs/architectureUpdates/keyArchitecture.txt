================================================================================
KEY-BASED STORAGE ARCHITECTURE
================================================================================
Per newReqs.txt and planTwo: the system uses Key = hash(data) as the primary
identifier. ProviderID is attached separately (not in the hash). CID is kept for
IPFS blockstore compatibility. The DHT routes tokens (physical locations), not
raw data.

1. Key Definition
   --------------
   - Key: SHA256 hash of data only. 32 bytes, hex-encoded for DHT keys.
   - KeyFromData(data []byte) Key: deterministic; same data yields same key.
   - ProviderID is never included in the hash. Same data from different peers
     yields the same Key, enabling deduplication and multi-provider routing.

2. Data Flow
   ----------
   Put:
     1. Key = KeyFromData(data)
     2. Block stored in IPFS blockstore (generates CID for compatibility)
     3. Datastore indexes: Key index, Key→CID mapping, Key→ProviderID mapping
     4. Local routing table: [Key, Providers, RepVector] updated
     5. Token synced to DHT (/tokens/<hex(key)) with Location{ProviderID, Address}

   Get:
     1. Check local: GetBlockByKey (Key→CID→blockstore)
     2. If not local: GetToken(key) from DHT → Location list
     3. DirectFetch to each Location in parallel (protocol /sng40/direct-fetch/1.0.0)
     4. Provider serves block by key; client verifies KeyFromData(blockData) == key

3. Datastore Namespaces
   --------------------
   - /manifest/key/<hex(key)        : presence of Key in manifest
   - /manifest/key-to-cid/<hex(key) : Key → CID mapping
   - /manifest/key-to-provider/<hex(key) : Key → ProviderID (local)
   - /manifest/index/<cid>          : CID presence (IPFS compatibility)

4. Local Routing Table
   -------------------
   - Entry: {Key, CID, Providers[], RepVector}
   - Key is primary; CID kept for IPFS. Get(Key) is O(1); GetByCID is O(n).
   - Supports multiple providers per key for replication.

5. Token Routing
   --------------
   - Token = {Key, Locations[], Timestamp, Version}
   - DHT key: /tokens/<hex(key)>. Locations hold ProviderID + Address.
   - DHT does not route block data; it routes tokens (physical locations).
   - GetToken is O(log N); DirectFetch is point-to-point.

6. Locking (Optional)
   ------------------
   - KeyLockManager: DHT-backed lock per Key for write mutual exclusion.
   - PutBlock/DeleteBlock acquire lock when KeyLockManager set.
   - Reads are lock-free (multiple concurrent reads allowed).

7. CID Role
   ---------
   - CID is derived from data for IPFS blockstore compatibility.
   - Bitswap and blockstore use CID internally.
   - All external APIs and routing use Key as primary identifier.
