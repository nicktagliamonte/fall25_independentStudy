================================================================================
TOKEN ROUTING MECHANISM
================================================================================
Per newReqs.txt: "the DHT routes tokens. tokens contain physical location of data."
The DHT does not route block data or provider announcements; it routes tokens
that carry Location (ProviderID + Address). Clients use tokens to perform
DirectFetch point-to-point. Token is stateless; its only function is to sync
with data.

1. Token Structure
   ---------------
   - Token: {Key, Locations[], Timestamp, Version}
   - Location: {ProviderID, Address (multiaddr), RTT (optional)}
   - Serialized as JSON for DHT storage. TTL 48h (libp2p DHT default).

2. DHT Namespace
   --------------
   - DHT key: /tokens/<hex(Key)>
   - UseTokenDHT=true: custom protocol prefix /sng40/kad/1.0.0 and
     NamespacedValidator("tokens") to allow arbitrary record format.
   - Incompatible with standard /ipfs DHT; use for token-routing or isolated nets.

3. Operations
   -----------
   PutToken: Store token in DHT. Validates Key non-zero, Locations non-empty.
   GetToken: Retrieve token by Key. O(log N) DHT lookup.
   UpdateTokenLocations: Replace locations; uses conflict resolution.
   PutTokenWithConflictResolution: Read-modify-write with optimistic concurrency.

4. Token Sync (Sync with Data)
   ---------------------------
   SyncTokenOnPut: On local Put, create token or append self to Locations.
   SyncTokenOnDelete: On local Delete, remove self from Locations; token gone if last.
   SyncTokenOnReplication: On replication, add new replica to Locations.
   Invoked by UpdateRoutingTableOnPut, UpdateRoutingTableOnDelete.

5. Conflict Resolution
   --------------------
   - Version field for optimistic concurrency. Increment on each update.
   - ResolveTokenConflict: Merge locations from both versions; dedupe by ProviderID;
     use higher Version, later Timestamp. Returns merged token with Version+1.
   - PutTokenWithConflictResolution: GetToken; if version mismatch, merge and retry.
   - UpdateTokenWithConflictResolution: GetToken, apply update fn, write with merge.
   - Retries with backoff (50ms * attempt) on conflict.

6. Read Path (Token-Based)
   -----------------------
   1. GetToken(key) from DHT -> Token with Locations
   2. DirectFetch to each Location in parallel (protocol /sng40/direct-fetch/1.0.0)
   3. Client sends key (hex); provider looks up by Key, returns block
   4. Client verifies KeyFromData(blockData) == key. First success wins.

7. TokenStore Abstraction
   ----------------------
   Stack.TokenStore: optional routing.ValueStore. When set (e.g. Gateway path),
   token sync uses TokenStore instead of DHT. Enables Gateway to route tokens
   via TupleSpace while storage uses DHT.
