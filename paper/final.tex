\begin{abstract}
Content-addressed storage systems efficiently retrieve immutable objects when
their identifiers are already known, but distributed applications often need a
different operation: discover and claim an object or task by its properties.
This paper presents \system, a distributed storage system with an integrated
tuple-space coordination plane. \system exposes \putop, non-consuming \readop,
and consuming \getop operations with associative matching while keeping
coordination metadata separate from bulk content transfer. Exact tuple
operations are assigned to deterministic owners in a Kademlia keyspace;
associative queries use hash-sharded distributed prefix indexes and
Bloom-filter summaries to identify candidate tuple names before contacting
their owners. The owner is
the serialization point for consuming operations, preventing two reachable
clients from claiming the same tuple. Tuple values can reference
content-addressed objects whose provider locations are maintained independently
and whose bytes are fetched directly over libp2p. This combination supports
decentralized workflows in which producers publish immutable inputs, workers
claim tasks by pattern, and results remain discoverable without a centralized
queue or metadata service. We describe the design, consistency boundary,
replication and repair mechanisms, and an evaluation methodology that separates
coordination costs from content-transfer costs.
\end{abstract}

tuple space, distributed storage, associative matching, content addressing,

\section{Introduction}

Content addressing gives distributed storage a stable answer to the question
``which bytes are requested?'' A client supplies a content identifier, the
network locates one or more providers, and the client verifies the returned
bytes against that identifier. Systems such as IPFS demonstrate that this model
can operate at Internet scale \cite{Trautwein2022}. It is less helpful when the
client does not yet know an identifier. A workflow worker may instead ask for
an unclaimed image-processing task for a particular data set; a monitoring
process may ask whether any result from a stage is available; and a repair
process may seek a peer offering storage in a suitable latency class. These are
associative coordination operations rather than exact content lookups.

Applications commonly answer such questions with a centralized database,
queue, or catalog layered above decentralized storage. That service restores a
distinguished failure and control point: content may remain replicated while
the application cannot discover work, assign it exclusively, or locate a
result. Tuple spaces offer an appealing coordination model because producers
and consumers communicate indirectly through tuples rather than through fixed
endpoints. \system adopts the tuple-space style of \putop, \readop, \getop, and
associative matching, but is an independent implementation contained in the
\system codebase; it does not embed or depend on the Linda system.

\system integrates this coordination model with a content-addressed data plane.
The tuple plane stores small application and system records. The data plane
stores immutable blocks and transfers them directly between providers and
requesters. A tuple may carry a content key and a set of provider locations,
but the associated bytes do not traverse the tuple space. This division avoids
turning associative coordination into a bulk-data broadcast.

Two design principles organize the system. An \emph{Active Content Addressable
Network} (ACAN) augments passive content identifiers with coordination records
that participate in discovery, placement, and repair. \emph{Statistic
Multiplexed Communication and Computing} (SMC2) uses observations of currently
available peers---including connectivity, round-trip time, storage offers, and
reputation when configured---to choose resources at operation time rather than
binding an object permanently to its original provider. These terms identify
implemented architectural responsibilities; they do not imply deterministic
service from unavailable resources or unlimited scalability.

This paper makes four contributions:
\begin{itemize}
    \item It defines a single tuple-space interface over a decentralized,
    content-addressed store, including explicit consistency semantics for
    publication, observation, and exclusive consumption, with correctness
    arguments stated over a stable ownership epoch.
    \item It presents a query-sensitive coordination plane that maps exact
    operations to deterministic owners and uses a Prefix Hash Tree (PHT) with
    Bloom-filter pruning for associative candidate discovery.
    \item It separates tuple metadata from verified direct content transfer and
    integrates opportunistic replication, RTT-aware placement, and repair.
    \item It implements the design over libp2p and provides an evaluation
    methodology for query scalability, exclusive claims, catalog growth,
    retrieval, and recovery.
\end{itemize}

\section{Motivating Workflow}
\label{sec:workflow}

Consider a scientific image-processing pipeline whose participants span
multiple administrative sites. A producer stores an immutable input object and
publishes a tuple named
\texttt{task:image:\emph{dataset}:\emph{id}}. The tuple value contains the
content key, operation parameters, and provider metadata. A worker searches for
\texttt{task:image:\emph{dataset}:*} and executes a consuming \getop. Exactly
one reachable worker obtains a given task tuple. It then resolves the content
key, fetches the bytes directly from a provider, verifies the hash, performs
the computation, and publishes a result tuple. Observers use \readop to inspect
progress without consuming results.

This example requires more than filename wildcarding. It combines decoupled
producers and consumers, associative discovery, exclusive work assignment,
immutable bulk data, and failure recovery. A centralized queue can provide
these properties, but it becomes the authority and availability dependency for
an otherwise peer-to-peer workflow. \system instead distributes tuple
ownership over the same peer substrate used to locate content.

\section{System Model and Semantics}
\label{sec:model}

\subsection{Model}

The system consists of peers connected by a time-varying network. Peers have
cryptographic libp2p identities and participate in a Kademlia overlay. Channels
may delay, reorder, or drop messages; operations can time out; and peers may
crash and later rejoin. The present design addresses crash and omission faults,
not Byzantine agreement. Content is immutable and verified by hashing the
received bytes. A malicious provider can withhold data, but cannot make altered
bytes validate under an uncompromised content key.

An exact tuple name maps to an owner in the Kademlia keyspace. During a stable
ownership epoch, requests that resolve to a reachable owner are serialized by
that owner. Ownership changes and owner failure require recovery from persisted
tuple state; Section~\ref{sec:limitations} states the resulting boundary.

\subsection{Operations}

The tuple space is a multiset: multiple tuples may have the same name and
value. Table~\ref{tab:semantics} summarizes its interface.

\begin{table}[t]
\caption{Tuple-space operations and consistency boundary.}
\label{tab:semantics}
\centering
\begin{tabular}{@{}lll@{}}
\toprule
Operation & Effect & Semantics \\
\midrule
\putop$(n,v)$ & publish one tuple & eventually discoverable \\
\readop$(p)$ & return a match & non-consuming \\
\getop$(p)$ & remove and return a match & exclusive at owner \\
\bottomrule
\end{tabular}
\end{table}

For an exact name, the client contacts the deterministic owner directly. For a
pattern, candidate discovery returns names that may match; the client then
contacts candidate owners. A \getop succeeds only when an owner removes the
tuple in the same critical section in which it selects the match. Concurrent
claimants may observe failures or timeouts, but two successful operations at
the same owner cannot consume the same stored tuple.

This guarantee is intentionally narrower than global transactional
serializability. \system does not provide multi-tuple transactions, atomic
operations spanning multiple owners, or linearizable observation during
ownership changes.

\section{Correctness Arguments}
\label{sec:correctness}

We state the central guarantees before describing their implementation. This
separates properties of the coordination abstraction from performance
characteristics of the particular overlay.

\begin{definition}[Tuple state]
Let $\mathcal{T}$ be a multiset of tuple instances. An instance
$t=(n,v,i)$ has name $n$, value $v$, and identity $i$. Distinct identities
allow duplicate names and values. For a pattern $p$, write $t \models p$ when
$n$ satisfies the system's matching relation.
\end{definition}

\begin{definition}[Stable ownership epoch]
An interval $E=[\tau_0,\tau_1]$ is a stable ownership epoch for name $n$ when
all operations on $n$ resolve to the same live owner $o(n)$ throughout $E$,
and messages between each participating client and $o(n)$ are eventually
delivered or return a failure.
\end{definition}

At an owner, tuple operations execute against one multiset under mutual
exclusion. Their state transitions are
\[
\begin{aligned}
\putop(n,v)&:\quad \mathcal{T}'=\mathcal{T}\uplus\{(n,v,i)\},\\
\readop(p)&:\quad \mathcal{T}'=\mathcal{T},\\
\getop(p)&:\quad
  \mathcal{T}'=\mathcal{T}\setminus\{t\}
  \quad\text{for one }t\in\mathcal{T}\text{ with }t\models p.
\end{aligned}
\]
If no matching instance exists, \readop and \getop return not found and leave
$\mathcal{T}$ unchanged.

\begin{lemma}[Read non-interference]
For any sequence containing only successful or unsuccessful \readop
operations, the tuple multiset is unchanged.
\end{lemma}
\begin{proof}
The \readop transition returns a copy of a matching value and assigns
$\mathcal{T}'=\mathcal{T}$. An unsuccessful read has the same state
transition. Composition preserves the multiset.
\end{proof}

\begin{theorem}[Owner-scoped exclusive consumption]
\label{thm:exclusive}
During a stable ownership epoch, a tuple instance can be returned successfully
by at most one \getop operation.
\end{theorem}
\begin{proof}
All operations for the tuple name execute at the same owner. The owner
serializes match selection and removal in one critical section. Consider the
first successful \getop that selects instance $t$. Its transition removes $t$
before the critical section is released. Every later \getop therefore observes
a multiset that does not contain $t$ and cannot return that instance. Thus no
two successful operations return the same tuple identity.
\end{proof}

\begin{proposition}[Conditional claim progress]
During a stable ownership epoch, if a matching tuple remains stored until a
\getop request reaches its owner, then that request either consumes a matching
tuple in finite local processing time or loses to an earlier serialized
consumer and returns not found.
\end{proposition}
\begin{proof}
Eventual delivery brings the request to the live owner. The owner's critical
section contains no blocking network operation. It therefore observes either
a matching instance, which it removes, or no matching instance after preceding
operations, in which case it returns not found.
\end{proof}

\begin{proposition}[Content verification]
\label{prop:integrity}
Let $k=H(b)$ be the requested content key for collision-resistant hash $H$.
A requester that returns bytes $b'$ only after checking $H(b')=k$ does not
accept altered bytes except with probability bounded by the collision or
second-preimage resistance of $H$.
\end{proposition}
\begin{proof}
Acceptance of altered bytes requires $b'\ne b$ and $H(b')=H(b)$, which is a
hash collision or second preimage. Provider voting is unnecessary for this
property.
\end{proof}

Theorem~\ref{thm:exclusive} deliberately excludes ownership changes. Persisted
owner state and an ownership-transfer protocol are required to extend the
result across epochs. Similarly, Proposition~\ref{prop:integrity} establishes
integrity, not availability: all providers may still be unreachable.

\section{Architecture}
\label{sec:architecture}

\subsection{Query-Sensitive Coordination Plane}

\system classifies operations by query shape. Exact tuple names use deterministic
Kademlia ownership. Prefix expressions descend a PHT, a trie-like index stored
over DHT operations \cite{RamabhadranPHT}. Substring expressions use
per-subtree Bloom summaries to prune branches that cannot contain all query
n-grams, followed by exact verification to remove false positives. Expressions
outside the indexed forms use peer search. This last path preserves generality
but may contact $O(N)$ peers, so the evaluation reports it separately.

PHT mutations are read-modify-write operations and cannot safely be issued
independently by every peer. \system hashes each full tuple name into one of
$S$ PHT shards, maps a distinct mutation key for each shard into the overlay,
and routes insertion or deletion to that shard's deterministic owner. The
owner serializes mutations within its shard, increments affected PHT-node
versions, and writes the nodes through the DHT. Namespace validation selects
the highest-version valid node. Hashing the full name avoids concentrating a
workload whose names share a prefix such as \texttt{task:} on one shard.

Prefix and substring queries read all shard indexes in parallel and merge
candidate names before contacting tuple owners. Queries therefore do not pass
through mutation owners. With balanced hashes, mutation capacity can grow with
$S$, while indexed query fanout is bounded by $S$ rather than the peer count
$N$:
\[
  C_{\mathrm{mutation}} \propto S,
  \qquad F_{\mathrm{query}} \le S.
\]
The evaluation varies $S$ because increasing write parallelism also increases
fixed query fanout.

The PHT and Bloom filter are established techniques rather than individual
novelties. \system contributes their placement within one tuple interface:
indexes discover candidate tuple names, while authoritative owners retain
consumption semantics. An index result is therefore a hint, not permission to
consume a tuple.

\subsection{Owner Protocol}

The owner resolver hashes the tuple name into the overlay keyspace and selects
the XOR-closest peer from the Kademlia result set, including the local peer.
Peers communicate with owners using a dedicated libp2p protocol. Each owner
maintains a concurrent tuple multiset. \putop appends an entry; \readop returns
the oldest matching entry without modification; and \getop selects and removes
the oldest matching entry under one mutex. Values are copied at the interface
boundary so callers cannot mutate stored state.

\subsection{Metadata and Content Separation}

Content blocks are addressed by SHA-256-derived keys. A routing token associates
a key with one or more provider identities and addresses. On retrieval, a peer
looks up the token, opens direct-fetch streams to providers, and accepts only
bytes whose computed key matches the requested key. This resembles the
provider-record role in IPFS and is not claimed as a novel provider/data
decoupling mechanism \cite{Trautwein2022,IPFSKademliaSpec}. The distinction in
\system is functional: the same coordination plane can carry application
tuples and active storage metadata, while bulk bytes remain outside it.

\subsection{Replication and Repair}

Each stored object has a configurable target replica count. The current upload
path creates replicas opportunistically among reachable peers. The repair path
classifies candidate locations using measured round-trip time and can seek
shortfalls in near, midrange, and far categories. Provider locations are merged
into the routing token and retrieval tries providers independently.

Replica count is a durability policy, not a Byzantine quorum. In particular,
the default count of seven does not by itself imply tolerance of two Byzantine
faults. Evaluation must distinguish replica creation from successful placement
across latency classes and from recovery after a provider loss.

\section{Implementation}
\label{sec:implementation}

The prototype is implemented in Go over libp2p. It includes a Kademlia DHT,
content-addressed block storage, provider-location tokens, direct block fetch,
a native tuple multiset, a tuple-owner stream protocol, PHT nodes stored through
a DHT value-store interface, hash-sharded incremental index maintenance,
per-shard mutation ownership, version-aware DHT validation, Bloom-filter
subtree summaries, a query router, replication and repair protocols, and an
HTTP control API. The legacy TSH adapter remains
available only as a compatibility option; the default \system path uses the
tuple-space implementation in the repository.

Tuple requests are size bounded and owner streams use deadlines. Exact
operations avoid scanning the overlay after ownership resolution. Pattern
queries separate candidate discovery from owner execution so stale index
entries can cause extra work but cannot duplicate a successful consume.

\section{Evaluation}
\label{sec:evaluation}

The evaluation is organized around five questions:
\begin{enumerate}
    \item What latency and routing work do exact tuple operations add?
    \item How do PHT and Bloom-assisted queries scale with catalog size, and
    how much traversal do Bloom summaries prune?
    \item Does owner serialization prevent duplicate claims under concurrency?
    \item How do catalog growth, upload, and remote retrieval compare with
    Swarm under equivalent cache and payload conditions?
    \item How quickly does the system restore its replica target after peer or
    latency-region failure?
\end{enumerate}

\subsection{Methodology}

Controlled experiments vary peer count, tuple count, index shard count, match
selectivity, payload size, and replication target. Each reported configuration uses fresh storage
where state affects results, discarded warm-up operations, multiple independent
trials, and confidence intervals. Remote retrieval bypasses the requester's
local store. Comparisons use the same payload, client path, cache state, and
timing boundary. Container experiments establish repeatability; experiments on
multiple physical hosts measure sensitivity to real network delay and failure
domains.

\subsection{Exclusive Consumption}

The claim test inserts one task and launches concurrent \getop operations from
multiple peers. The primary safety metric is the number of successful
consumers, which must equal one. Secondary metrics are claim latency, timeout
rate, and throughput as independent tuple names increase.

\subsection{Associative Query Cost}

Exact, prefix, substring, and general-pattern workloads use the same tuple-name
distribution. Measurements report latency, contacted peers, fetched PHT nodes,
Bloom-pruned branches, false-positive candidates, and returned matches. An
ablation disables Bloom summaries to isolate their effect.

\subsection{Storage and Recovery}

Catalog-growth tests measure upload and cold remote retrieval as distinct
objects accumulate. Failure tests remove providers after replication,
partition latency classes, and observe availability and time to restore the
target count. Results report achieved rather than configured replica diversity.

\section{Related Work}
\label{sec:related}

\paragraph{Tuple-space coordination.}
The tuple-space model is associated with Linda and subsequent work separating
coordination from computation \cite{Gelernter1985,CarrieroGelernter1989}.
\system adopts the familiar operation style but implements its own distributed
ownership, indexing, storage integration, and failure behavior.

\paragraph{DHTs and associative indexes.}
Kademlia provides logarithmic expected routing through XOR distance
\cite{MaymounkovKademlia}. DHTs primarily support exact lookup. PHT extends
their interface with prefix and range queries \cite{RamabhadranPHT}, while
Bloom filters compactly summarize set membership \cite{Bloom1970}. \system uses
these structures for candidate discovery but returns consuming authority to a
tuple owner.

\paragraph{Decentralized storage.}
IPFS combines content addressing, provider discovery, and peer-to-peer block
exchange \cite{Trautwein2022}. Bitswap uses content-routing information for
parallel block exchange \cite{deLaRochaBitswap}. Swarm provides a layered
peer-to-peer storage and communication infrastructure \cite{SwarmWhitepaper}.
\system builds on this design space but focuses on associative application
coordination coupled to content storage, not on claiming that provider records
or direct provider transfer are new.

\section{Limitations}
\label{sec:limitations}

The current ownership protocol provides exclusive consumption only while
clients agree on and can reach the authoritative owner. Durable owner state,
ownership transfer, and reconciliation after divergent overlay views must be
validated before claiming availability-preserving failover for tuple
coordination. Mutations within each index shard are serialized by its elected
owner; a hot shard can therefore bottleneck even when aggregate mutation load
is balanced. Indexed queries contact every configured shard, making the shard
count a write-parallelism/query-fanout tradeoff. General regular-expression
search may require network-wide work.
Bloom filters reduce negative traversal but do not remove false positives.
RTT categories approximate network distance and do not guarantee independent
geographic or administrative failure domains. Finally, container clusters on
one host test protocol scaling and repeatability, not Internet deployment;
multi-host experiments are necessary for claims about regional resilience.

\section{Conclusion}

\system treats content-addressed storage as a substrate for distributed
applications rather than as an endpoint requiring every client to know a
content identifier. Its native tuple-space plane supports indirect publication,
observation, and exclusive work claiming while routing bulk bytes directly
between storage peers. The architecture combines ACAN's active metadata with
SMC2's runtime resource selection, deterministic tuple ownership, associative
candidate discovery, and explicit replication and repair. Equally important,
the design states where its guarantees stop: exclusive consumption belongs to
a stable reachable owner, content integrity comes from content addressing, and
replica counts are durability policy rather than consensus quorums.
